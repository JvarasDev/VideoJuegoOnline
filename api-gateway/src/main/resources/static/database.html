DATABASE PER SERVICE PATTERN
Pregunta de Defensa: "¿Por qué no usar una sola base de datos centralizada gigante para todos los microservicios?"

Respuesta Táctica: Si todos los servicios apuntan a una misma base de datos, violamos el principio de independencia. Si la BD monolítica se cae, se cae todo el sistema. Si un servicio cambia el nombre de una columna, rompe a los demás.

Solución: Implementamos "Database-per-Service". Cada microservicio (Inventario, Usuario, Mision) tiene su propio esquema de datos. Si un servicio necesita datos de otro, debe pedirlos vía API REST (Feign), nunca consultando directamente la base de datos de su compañero.

DATABASE MIGRATIONS (FLYWAY)
Para mantener los esquemas de bases de datos sincronizados a través de los múltiples servicios sin usar scripts manuales que el equipo olvide ejecutar, se emplea un sistema de versionado de BD (Ej: Scripts V1, V2).

Al levantar un microservicio, Spring arranca los scripts SQL (como V2__agregar_columna_nombre_item.sql) garantizando que la estructura de la base de datos coincida con la versión del código.
// DECRYPTED PAYLOAD: V2__agregar_columna_nombre_item.sql ALTER TABLE inventario ADD COLUMN nombre_item VARCHAR(255) NOT NULL;
